Principios de producción específicos — Parte 2
P1 · stack y restricciones
Pipeline en n8n + Anthropic Claude API. Capa gratuita: Sheets + SMTP + Telegram. Coste estimado ~20 €/mes a 1500 POs. Python aparece como alternativa documentada (Nanobot/script standalone en II5; Streamlit dashboard en II6), nunca obligatoria para el alumno.
P2 · arco acumulativo
Cada sesión añade una capa que entra en la siguiente. II1 ingesta + canal → II2 reglas R01–R09 deterministas → II3 LLM semántico (Claude) → II4 routing y notificación → II5 resiliencia + alternativa Python → II6 MVP completo + dashboard.
P3 · LLM = extractor estructurado
El patrón E5 es arquitectura obligatoria: el LLM extrae entidades del texto libre, nunca decide prioridad ni valida catálogo. Las reglas R01–R09 son JS determinista en Code nodes. El parser anti-alucinación verifica part_number_proveedor contra catálogo VBX-COMP y fuerza a null si el LLM lo inventó.
P4 · regla R09 anti-duplicado
El agente nunca registra dos veces la misma numero_pedido. Lookup contra Sheets Pedidos en cada PO. Esta regla se introduce como stub en II2 (cache hardcoded) y se sustituye por lookup real en II4.
P5 · schema VERBEX estricto
El JSON canónico está definido en spec § 4.4. Toda salida del pipeline debe parsear contra ese schema. Los 5 ejemplos few-shot del SKILL son el contrato visible. Output siempre JSON, nunca markdown ni prosa libre.
P6 · planteamiento previo siempre
El flujo de trabajo es invariable: planteamiento → aprobación → producción secuencial. Para cada sesión de Parte 2 se presenta el planteamiento antes de generar ningún material didáctico. El código MVP-A ya validado es la fuente de verdad técnica.

Sesión II1 · Módulo II1
Ingesta y Conectividad Multi-Canal
El agente busca datos él solo · PRDA: Percibir
2,5 h
Idea fuerza Telegram es el punto de entrada único, pero hay 3 canales detrás: email PDF, HelionLink CSV y portal web. El agente filtra el remitente por chat_id antes de cualquier procesamiento, identifica el canal por heurística sobre la estructura del texto, y devuelve un contrato de datos de 7 campos. Sin LLM, sin Sheets, sin reglas — solo limpia y prepara.
Contenido teórico (50 min)
  • Bot Telegram como entry point unificado · @BotFather + token + chat_id allowlist
  • Filter v2 con CSV-includes para autorizar remitentes (TELEGRAM_ALLOWED_CHAT_IDS)
  • Heurística de canal: HELIONLINK o ≥5 campos pipe-separados → helionlink_csv · "portal web" → portal_web · resto → email_pdf
  • Code node v2: lookup chat_id → codigo_erp + preprocesado (trim 4 000 chars, normalización saltos)
  • Contrato de salida: 7 campos (texto_limpio · chat_id · codigo_erp_detectado · canal_detectado · from_username · fecha_hoy · timestamp_recepcion)
Inputs
Token Telegram bot · clientes.csv (mirror in-memory) · 4 payloads de prueba
Outputs
JSON 7 campos (contrato para II2/II3)
Reglas
chat_id en allowlist · texto no vacío · trim 4000 chars · normalización saltos línea
Excepciones
chat_id desconocido → codigo_erp_detectado: null (no rompe) · texto vacío → Filter descarta

Sesión II2 · Módulo II2
Lógica Determinista R01–R09
Razonamiento sin alucinaciones · PRDA: Razonar (capa determinista)
2,5 h
Idea fuerza El núcleo del principio E5: las reglas de negocio no las decide el LLM. Son JavaScript determinista en Code nodes de n8n. R01 (AOG override), R02 (fecha urgente), R03 (confianza baja), R04 (PN desconocido), R05/R06 (CoC/EASA), R07 (cliente nuevo), R08 (cantidad inválida), R09 (duplicado). El LLM extraerá texto en II3; aquí construimos la capa que nunca alucina.
Contenido teórico (50 min)

  • Orden de aplicación: R04+R08 (validación) → R07 (cliente) → R01+R02 (prioridad) → R05+R06 (cert) → R03 (confianza) → R09 (duplicado)
  • Mirrors in-memory de equivalencias_pn y clientes como anti-patrón didáctico (workflow autónomo y portable)
  • 8 casos de prueba (po_test_set.json): 01_estandar · 02_aog · 03_amendment · 04_pn_desconocido · 05_cliente_nuevo · 06_fecha_urgente · 07_cantidad_invalida · 08_po_duplicada

Outputs

Reglas

Excepciones

Sesión II3 · Módulo II3
Capa Semántica · Claude API
El LLM extrae estructura, no calcula · PRDA: Razonar (capa cognitiva)
2,5 h
Idea fuerza El LLM recibe texto libre y devuelve un JSON contra schema VERBEX. Pero el modelo es falible: puede inventar part_number_proveedor, devolver markdown o saltarse el schema. Un parser anti-alucinación valida cada respuesta y bloquea inventos antes de pasar a las reglas R01–R09. Esta sesión es diseño de prompt industrial, no magia.
Contenido teórico (50 min)
  • HTTP Request a Anthropic API · modelo claude-sonnet-4-20250514 · temperature: 0.1 · max_tokens: 1500
  • System prompt en template literal JS: SOUL (identidad VERBEX + 7 reglas absolutas) + SKILL (tablas autoritativas: 5 clientes · 7 equivalencias PN · catálogo 16 refs · banda confianza)
  • 5 ejemplos few-shot embebidos: E1 PO estándar · E2 HelionLink CSV · E3 AOG · E4 Amendment · E5 PN desconocido
  • Parser anti-alucinación (Code node): extrae JSON · limpia ```json fences · valida schema mínimo · verifica PN proveedor contra catálogo · fuerza null + alerta si inventado
  • Coste estimado ~0,012 €/PO (input ~1900 + output ~300 tokens) · ~20 €/mes a 1500 POs
Inputs
Texto PO libre · ANTHROPIC_API_KEY en HTTP Header Auth (x-api-key) · catálogo + equivalencias en mirror del prompt
Outputs
JSON validado contra schema VERBEX (spec § 4.4) · enriquecido por R01–R09
Reglas
El LLM no calcula precios ni totales · output siempre JSON · cita obligatoria de PN existente en catálogo
Excepciones
Texto fuera de JSON → parser rechaza · timeout API → onError: continueErrorOutput · error: no_pedido → log + estado ERROR

Decisiones tomadas durante el desarrollo del MVP-A
D1 · Canales de ingesta
Telegram como entry point único + 3 canales detectables por heurística sobre la estructura del texto: email_pdf (default · texto libre) · helionlink_csv (≥5 campos pipe-separados) · portal_web (mención explícita). El bot Telegram lo proporciona el alumno con @BotFather; los chat_id autorizados se listan en TELEGRAM_ALLOWED_CHAT_IDS (CSV). Afecta a M3/M4 de II1.
D2 · Google Sheets como persistencia
Cada alumno crea su propio Sheet VERBEX-Pedidos con 4 hojas (Pedidos · Lineas · Errores · Clientes), genera Service Account JSON desde Google Cloud Console y comparte el Sheet con el email del Service Account (rol Editor). GOOGLE_SHEETS_ID + ruta JSON en .env. Spec § 7 default D2. Sheets-schema completo en M2 de II4.
D3 · Canales de notificación
Telegram primario como canal de operación: TELEGRAM_CHAT_ID_PRODUCCION (AOG/PRIORITARIO) · TELEGRAM_CHAT_ID_CALIDAD (CoC/EASA Form 1) · operador (duplicados + errores). SMTP secundario para confirmación al cliente final con email branded VERBEX. Sin Slack en MVP-A.
D4 · Observabilidad
