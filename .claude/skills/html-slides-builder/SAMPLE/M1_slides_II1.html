Propósito de esta sesión: limpiar el canal de entrada y entregar un contrato de datos consistente. La complejidad crece en II2 (reglas) e II3 (LLM). II1 es deliberadamente mínimo.
Heurística de canal
3 canales · detección por estructura del mensaje
email_pdf
PO en texto libre
Correos, PDF escaneados, WhatsApp. El canal por defecto cuando no se detecta ningún patrón estructural.
→ Caso payload 01, 03, 04
helionlink_csv
CSV pipe-separated
Contiene la palabra HELIONLINK o ≥ 5 campos separados por | en la misma línea.
→ Caso payload 02
portal_web
Portal Kairos Defense
Menciona Kairos Defense o portal web. Detección por palabras clave.
→ No hay payload de prueba (raro)
Regla de prioridad: se evalúan en orden helionlink_csv → portal_web → email_pdf. El primero que encaja gana. Si ninguno encaja, el canal es email_pdf por defecto.
Nota pedagógica: esta heurística es simple porque los 3 canales de VERBEX son visualmente muy distintos. La detección semántica de urgencias AOG llega en II3 con el LLM.
Nodos 1 y 2
Telegram Trigger · Filtro chat_id autorizado
Nodo 1 Telegram Trigger
Escucha mensajes entrantes en el bot VERBEX. Requiere:
  • Token de bot (desde @BotFather)
  • Credencial Telegram Bot · VERBEX configurada en n8n
  • Solo evento message activado
Nodo 2 Filtro chat_id autorizado
Descarta mensajes antes de ejecutar código. Condición AND:
  • chat_id está en TELEGRAM_ALLOWED_CHAT_IDS (env var CSV)
  • El mensaje tiene texto no vacío
Expression // Condición del Filtro — se evalúa en n8n Expression left: {{ ($env.TELEGRAM_ALLOWED_CHAT_IDS || '').split(',').map(s => s.trim()).includes($json.message.chat.id.toString()) }} op: boolean is true AND left: {{ $json.message.text }} op: string is not empty
Variable de entorno: TELEGRAM_ALLOWED_CHAT_IDS=123456789,234567890,... — separar por comas, sin espacios obligatorios (el código hace trim).
Nodo 3
Detectar canal y preprocesar — el núcleo del módulo
Lookup chat_id → ERP
Mirror in-memory de data/clientes.csv. Si el chat_id no está en el mapa → null (no rompe el flujo).
Limpieza de texto
Trim · colapsar espacios múltiples · normalizar \r\n → \n · truncar a 4 000 chars si el mensaje es gigante.
JavaScript // Heurística de canal (en orden de prioridad) let canal = 'email_pdf'; // default if (texto.includes('HELIONLINK') || (texto.includes('|') && texto.split('|').length >= 5)) { canal = 'helionlink_csv'; } else if (/kairos[\s\-\.]?defense|portal[\s\.\-]web/i.test(texto)) { canal = 'portal_web'; } // El nodo Set (Stub salida) filtra a exactamente 7 campos
IO · RE
Contrato completo del módulo II1
Inputs
  • Token Telegram bot (TELEGRAM_BOT_TOKEN)
  • Lista de chat_id autorizados (TELEGRAM_ALLOWED_CHAT_IDS)
  • Mirror in-memory de data/clientes.csv (chat_id → codigo_erp)
  • Payloads de prueba (payload_01…04.txt)
Outputs — 7 campos
  • texto_limpio — string ≤ 4 000 chars
  • chat_id — string
  • codigo_erp_detectado — string | null
  • canal_detectado — email_pdf | helionlink_csv | portal_web
  • from_username — string
  • fecha_hoy — YYYY-MM-DD
  • timestamp_recepcion — ISO 8601 UTC
Reglas
  • Solo chat_id en lista autorizada pasa el filtro
  • Texto vacío → descartado (no llega al Code)
  • Texto > 4 000 chars → truncado
  • \r\n, \r → \n · espacios múltiples → un espacio
  • Prioridad canal: helionlink_csv → portal_web → email_pdf
Excepciones
  • chat_id desconocido → codigo_erp_detectado: null — flujo continúa; II2 trata el caso "cliente nuevo"
  • Texto vacío → Filter descarta antes de llegar al Code
  • chat_id no autorizado → Filter descarta
  • Mensaje AOG → email_pdf (semántica en II3)
